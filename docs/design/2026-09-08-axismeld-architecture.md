# AxisMeld 架构设计

- 状态：待最终审核
- 日期：2026-09-08
- 产品名称：AxisMeld
- 产品说明：Maya-style modeling workflow, built on Blender.

## 1. 项目定位

AxisMeld 是一个可直接拉取、构建和运行的 Blender 源码衍生项目，不是单独安装后才能工作的快捷键插件。它以 Blender 为技术基础，以 Maya 2026 默认交互为公开基线，首先服务于建模、视图导航、选择、热盒和 UV 编辑工作流。

项目保留 Blender 的场景、网格、依赖图、渲染、文件格式和扩展生态，避免为了模仿 Maya 而复制一套平行的三维内核。需要改变的是艺术家的交互层和少量必须进入核心的编辑器能力。

除继承的 Blender 上游代码和第三方依赖外，AxisMeld 的全部新增代码、测试、构建脚本及项目文档均由 AI 完成。人类负责提出目标、制定需求、进行产品与技术取舍，以及最终审核和验收；每项 AI 产出仍必须通过本项目规定的代码审查、测试和构建门槛。

### 1.1 成功标准

1. 新用户构建并启动 AxisMeld 后，不安装额外插件即可选择 Maya 2026 基线配置并开始建模。
2. Maya 默认命令在 AxisMeld 中有可追踪的一一语义映射；无法等价实现的命令必须标记差异，不能静默替换成近似行为。
3. 用户个人按键修改以独立覆盖层保存，可以随时回到公开基线，也不会污染其他使用者的默认体验。
4. 热盒、视图切换和高频建模操作在按下、保持、拖动和释放阶段具有稳定、可测试的状态行为。
5. Blender 上游主干更新可以持续合并；冲突集中在少量明确的集成接缝，而不是散布在编辑器代码中。
6. UV 编辑器可以进行长期的大幅扩展，同时继续使用 Blender 的网格与 UV 数据，并保持 `.blend` 文件兼容。

### 1.2 非目标

- 不复制 Maya 的界面布局、视觉资产、源代码、专有算法或受保护品牌素材。
- 不把 Blender 所有动画、绑定、渲染和合成工作流一次性改造成 Maya。
- 不承诺第一阶段就达到完整 Maya 功能对等。
- 不以补丁数量或外观相似度为目标；优先保证操作语义、效率、稳定性和上游可维护性。

## 3. 上游同步与分支模型

Git 远端约定：

- `upstream`：Blender 官方仓库，只获取上游历史。
- `origin`：AxisMeld 项目仓库。

长期分支：

- `main`：本地只读镜像 Blender `upstream/main`，不直接承载 AxisMeld 开发提交。
- `axismeld/integration`：持续合并 Blender `upstream/main`，承接日常开发和冲突处理。
- `axismeld/stable`：从通过验证的集成节点产生，面向可复现构建与日常制作。

同步规则：

1. 合并 Blender 上游时保留 merge commit，记录对应上游提交和冲突决策。
2. 不在上游镜像提交上改写历史，也不通过大规模格式化制造无意义差异。
3. 每个核心补丁必须归属一个明确的 AxisMeld 子系统，并有维护原因和回归测试。
4. 能通过扩展 API 或数据配置实现的行为不进入 Blender 核心补丁。
5. 每次稳定发布都记录 Blender 基线提交、AxisMeld 提交、构建工具链和依赖版本。

## 4. 总体架构

AxisMeld 采用“薄核心衍生层 + 内置第一方模块 + 分层配置”的结构。

### 4.1 薄核心衍生层

核心层只承载必须接入 Blender 原生事件系统、编辑器状态或性能敏感算法的能力：

- 输入事件和按下/释放状态的必要接缝。
- 热盒与视图切换所需的原生区域、窗口和事件路由接缝。
- UV 编辑器需要的底层选择、几何运算或绘制接口。
- 面向第一方模块的窄而稳定的 RNA、operator 或 C/C++ 接口。

核心层不直接编码大量快捷键表、菜单内容和个人配置。

### 4.2 第一方内置模块

随 AxisMeld 构建和发行，但按清晰接口与核心解耦：

- `workflow_commands`：语义命令注册与能力查询。
- `maya_input`：Maya 2026 基线键位、修饰键与上下文解析。
- `hotbox`：热盒和 marking menu 的状态机、布局与命令调用。
- `maya_view`：视图导航、单视图与四视图切换、摄像机相关交互。
- `modeling_tools`：不能由已有 Blender operator 准确表达的建模工作流。
- `uv_workspace`：UV 编辑器界面、交互与工作区编排。
- `uv_tools`：UV 选择、拓扑、展开、优化和布局算法。
- `profile_manager`：基线、项目和用户覆盖配置的加载、迁移和诊断。

### 4.3 第三方扩展兼容

普通 Blender 扩展继续通过标准 Python API、operators、keymaps 和 UI 注册机制运行。AxisMeld 的第一方模块不得占用或更改不相关的 Blender API。新增能力首先通过可选的 AxisMeld Workflow API 暴露；第三方扩展不知道该 API 时仍应按 Blender 原有方式工作。

## 5. 语义命令系统

快捷键不直接绑定一串易变的 Blender operator 参数，而是先指向稳定的语义命令标识，例如：

- `selection.object_mode`
- `selection.vertex_mode`
- `transform.move`
- `view.focus_selected`
- `hotbox.open`
- `uv.cut`
- `uv.sew`

每个语义命令记录：

- Maya 2026 命令名称和默认输入。
- AxisMeld 命令标识与适用上下文。
- Blender 实现入口及版本适配器。
- 对等状态：`exact`、`adapted`、`unsupported`。
- 已知行为差异和测试用例。

这一层隔离 Blender operator 改名、参数变化和上下文调整，使快捷键基线不必随着每次上游更新整体重写。

## 6. 输入、热盒与视图

### 6.1 输入模型

输入系统必须区分：

- 单击、双击、按下、保持、拖动和释放。
- 键盘左右修饰键及组合顺序。
- 3D 视图、UV 编辑器、Outliner 和文本输入等上下文。
- 临时工具状态与永久模式切换。

Maya 2026 默认按键表是只读基线。AxisMeld 的版本适配只调整实现映射，不修改基线含义。

### 6.2 热盒

热盒不是普通弹出菜单，而是由事件驱动的状态机：

1. Space 按下后进入候选状态。
2. 达到保持阈值或发生定向拖动时打开热盒或 marking menu。
3. 指针方向、区域和修饰键决定菜单集合。
4. 释放时确认目标或安全取消。
5. 未触发热盒的短按按照当前上下文执行视图最大化或视图切换行为。

阈值属于可配置参数，并通过自动化事件序列测试，避免依赖帧率或机器性能。

### 6.3 视图体验

第一阶段还原 Maya 用户最依赖的行为：

- 单视图与四视图之间快速切换。
- 当前鼠标所在面板成为切换焦点。
- Maya 风格的轨道旋转、平移、缩放和选中聚焦。
- 透视、正交和标准方向视图的可预测切换。
- 不强制复制 Maya 的整体窗口布局。

## 7. 配置分层

配置按优先级从低到高合并：

1. `maya2026-default`：项目维护的只读公共基线。
2. `axismeld-version-adapter`：适配特定 Blender 基线的实现差异。
3. `studio-profile`：团队或项目约定，可选。
4. `user-profile`：用户个人覆盖；维护者的轻微修改放在这里。
5. `session-overrides`：当前会话临时修改，不自动写回配置。

每个覆盖项只保存与下一层的差异。配置文件带 schema 版本，并提供迁移、冲突报告、恢复基线和导出功能。公共发行版不得把维护者个人覆盖误打包成默认配置。

## 8. UV 编辑器长期设计

UV 编辑器是独立核心子系统，不以一个大型 Python 插件堆积功能。它需要同时满足交互效率、算法能力、上游可合并性和数据兼容性。

### 8.1 边界

- 继续使用 Blender Mesh、BMesh、UV attribute 和 `.blend` 数据。
- 对 Blender `editors/uvedit` 与 `editors/space_image` 只增加必要注册点和窄接口。
- 新的算法、命令编排和界面行为分别放在独立模块中。
- UI 不直接依赖算法内部结构，算法也不依赖具体面板布局。
- 每项能力都通过语义命令系统调用，便于快捷键、热盒、菜单和脚本共享。

### 8.2 能力路线

UV 工作按独立里程碑逐步实现：

1. 选择语义与 UV shell 操作。
2. Cut、Sew、Move and Sew、Split、Stitch 等拓扑编辑。
3. Align、Straighten、Orient、Stack 与对称操作。
4. Unfold、Optimize、Relax 及固定点约束。
5. Layout、texel density、padding、UDIM 和批量处理。
6. Checker、畸变、重叠、边界与密度可视化。
7. 工具历史、重复执行、预设和生产诊断。

这里的“达到 Maya UV 编辑器水平”以经过验证的任务流程、结果质量和操作成本衡量，不以菜单名称或视觉复制衡量。

### 8.3 性能与正确性

- 核心几何算法使用可测试的数据输入输出，不把算法藏在 UI 回调里。
- 大网格操作提供取消、进度和一致的撤销边界。
- 算法测试覆盖退化面、非流形边、多个 UV 层、UDIM、镜像和高面数模型。
- 对影响文件数据的变更执行 Blender 原版往返读写测试。

## 9. 兼容与失败处理

- AxisMeld API 使用独立命名空间和显式版本号。
- Blender API 不存在时，适配层返回能力缺失和可读诊断，不让热盒调用静默失败。
- 配置迁移失败时保留原文件，生成迁移报告并回退到公共基线。
- 第三方插件快捷键冲突可以检测、列出来源并让用户选择，不自动覆盖插件配置。
- 合并上游后，任何 `exact` 映射退化为近似行为都视为回归。

## 10. 验证体系

### 10.1 每次提交

- 配置 schema 与命令表静态校验。
- 输入状态机单元测试。
- 语义命令上下文测试。
- 受影响模块的 Blender 测试。

### 10.2 每次上游合并

- Blender 官方测试集中的相关部分。
- Maya 基线快捷键映射完整性检查。
- 热盒按下、拖动、释放和取消的事件回放。
- 单视图、四视图与上下文焦点回归测试。
- UV 数据往返、撤销和关键算法基准。
- 第三方扩展冒烟测试集合。

### 10.3 稳定发布门槛

- Windows 可复现构建通过；其他平台在进入支持范围后使用相同门槛。
- 干净用户目录首次启动通过。
- 公共基线与维护者个人覆盖分别加载通过。
- 打包产物显示正确的 AxisMeld 品牌、上游基线、许可证和独立性声明。
- 安装包和压缩包不包含个人路径、凭据或未声明的二进制依赖。

## 11. 分阶段交付

### 阶段 0：上游与构建基线

导入 Blender 上游历史，建立 Windows 构建、版本标识、远端与合并验证流程。该阶段不追求操作差异。

### 阶段 1：输入与配置基础

实现语义命令注册、Maya 2026 默认基线、分层配置和个人覆盖。先覆盖建模最常用的选择、变换和模式切换。

### 阶段 1.1：基础操纵器交互对齐

在热盒之前补齐移动、旋转、缩放的点选轴保持、空白区域中键约束拖动、确认、取消和撤销。
保留原生直接拖动，通过窄原生接缝扩展事件行为，不重写变换计算。
增加真实事件回放和工具切换耗时测量；F8–F11 初次失效暂列未复现，不做猜测性修复。
详见 `2026-09-09-phase-1-1-manipulator.md`。

2026-09-09 用户决定：物体模式 Global 缩放差异 **AXM-COMPAT-001** 暂时搁置，
保留 Blender 原生行为，不阻挡阶段 2。后期建模变换专题再评估；详见
[兼容性记录](../compatibility/global-object-scale.md)。此次延期不代表差异已解决，
也不替代阶段 1.1 尚未完成的独立审查和集成门槛。

### 阶段 2：热盒与视图

交付可日常使用的 Space 状态机、热盒、marking menu、单视图/四视图以及 Maya 风格导航。

2026-09-09 已确认阶段 2A 的四项范围：Space 短按布局切换、按住热盒、四向视角菜单、
各面板会话内视角恢复。详见 [阶段 2A 开发规格](../superpowers/specs/2026-09-09-phase-2a-hotbox-views-design.md)，
该规格待用户审核，尚未进入实施；后续再扩展完整热盒菜单。

### 阶段 3：建模工作流

补齐上下文敏感的选择、组件模式、变换枢轴、挤出、合并、切割和重复操作，建立完整对照矩阵。

### 阶段 4：UV 基础替换

启用独立 UV 工作区、选择语义、shell 操作、Cut/Sew 和测试框架，不一次性替换所有 Blender UV 功能。

### 阶段 5：UV 生产能力

逐步交付展开、优化、布局、UDIM、密度和诊断能力，并以真实制作任务验证性能和结果。

## 13. 已确认决策

- 正式品牌为 AxisMeld。
- 项目是可直接构建运行的 Blender 衍生版本，不是单一插件。
- Blender 上游主干可以持续合并。
- Maya 2026 默认快捷键是公共基线。

- UV 编辑器按可大幅扩展的独立子系统设计。
- 除 Blender 上游代码和第三方依赖外，AxisMeld 的新增工程实现完全由 AI 完成，人类负责目标、取舍和最终验收。
- 官方运营完全非盈利，允许透明的成本型捐赠。
- 非盈利运营不限制 GPL 允许的商业创作或再发行。
